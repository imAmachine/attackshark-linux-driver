# Audit report — attackshark-linux-driver

Отчёт о качестве кодовой базы на момент коммита `729150b`. Составлен
одноразово, код не менялся. Задача этого файла — служить чек-листом для
агентов, которые будут чинить найденное.

**Как проверялось:** прочитаны все файлы `src/`, `include/`, `src/gui/`,
`Makefile`, `systemd/`, `udev/`, `etc/`; из `tests/` подробно — `test_codec.c`,
`test_keyboard.c`, `test_transport.c`. Прогнаны `make test`, `make test-ui`,
`make gui`, сборка с `-fsanitize=address,undefined`, точечный 30-строчный
репро на реальном `src/hidraw.c`.

**Предполагаемая нагрузка:** один пользователь за рабочим столом, GUI открыт
постоянно, одновременно подключены мышь и клавиатура (то есть **два потока
ввода-вывода**), CLI может работать параллельно.

**Статус сборки:** чистое дерево собирается, `make test` и `make test-ui`
проходят. Найденные ниже дефекты тестами не ловятся.

## Правила для агента

1. Порядок работ: **A1 → A2**, затем B3, B4, остальное по желанию. A1 меняет
   `hidraw.c`, от которого зависят все тесты; делать его первым.
2. Одна задача = один коммит. Не смешивать «must fix» и «lean» в одном
   патче: lean-удаления маскируют поведенческие правки в диффе.
3. После каждой задачи обязательны: `make clean && make test`,
   `make test-ui`, `make gui` (если GTK4 есть), и проверка из поля
   **Проверка** ниже.
4. Не добавлять слои, конфиг и зависимости. Все правки ниже — удаление или
   несколько строк.
5. Публичный API `include/attackshark.h` ломать нельзя, кроме удаления
   `as_keyboard_set_light_power` (A2) — она нигде не используется.
6. Номера задач — стабильные идентификаторы, а не порядок: A2 и B13 ниже
   появились после правки отчёта (см. «История»), поэтому идут вразнобой.
6. Не трогать `docs/PROTOCOL.md` и форматы пакетов: они сверены с железом.

## A. Must fix

### A1. Процесс убивает сам себя своим таймерным сигналом

**Файлы:** `src/hidraw.c` — `with_timeout()`, блоки `restore_handler` /
`restore_mask`; `on_timeout()`.

**Симптом.** Случайное падение всего процесса с кодом 128+64 (`Real-time
signal 30` в шелле) при вводе-выводе. В GUI выглядит как «приложение
закрылось».

**Причина (доказана).** `with_timeout()` ограничивает блокирующий `ioctl`
через POSIX-таймер (`SIGEV_THREAD_ID`, сигнал = «первый свободный real-time
сигнал», интервал 1 мс). Выбор сигнала и установка обработчика защищены
мьютексом `timeout_lock`, но мьютекс отпускается сразу после установки —
на весь остальной вызов сигнал никем не помечен как занятый. Поэтому два и
более потока выбирают **один и тот же** сигнал (в логе репро: три потока на
сигнале 64). Первый завершившийся поток возвращает `SIG_DFL`, после чего тик
чужого таймера с действием по умолчанию убивает процесс.

Это не теория: в GUI `src/gui/as-worker.c` создаёт по потоку на каждое
устройство, поэтому мышь + клавиатура = ровно этот сценарий.

**Воспроизведение.**
```sh
make clean
make test CFLAGS="-O1 -g -fsanitize=address -fno-omit-frame-pointer" \
          LDFLAGS="-fsanitize=address"
# падает на tests/test_transport: "Real-time signal 30", exit=192, 5 из 5
```
На обычной сборке тот же код проходит — только за счёт удачного тайминга.

**Правка (минимальная).** Обработчик ставится один раз и **никогда не
возвращается к `SIG_DFL`**: тогда «протухший» тик безвреден, `on_timeout`
просто выставит флаг не тому потоку (`on_timeout` уже фильтрует по
`si_value`, так что чужой тик ничего не делает).
- Убрать из `with_timeout()` сохранение/восстановление `old.sa_handler`
  (переменную `old` в блоке `restore_handler` и его `goto`).
- Держать один выделенный сигнал (static `int`, инициализируется при первом
  входе под `timeout_lock`), а не сканировать диапазон при каждом вызове.
- `sigtimedwait`-дренаж оставить: он чистит очередь, но теперь не критичен.

**Правка (лучше, если хватит времени).** Убрать сигналы вовсе: `timerfd_create`
+ `poll()` перед `ioctl`. Тогда время ожидания ограничивается без
обработчиков и без общего состояния между потоками. Меняет ~60 строк, но
убирает целый класс ошибок.

**Проверка.**
- `grep -n "restore_handler\|SIG_DFL" src/hidraw.c` — упоминаний `SIG_DFL`
  в `with_timeout` не осталось.
- Сборка из блока «Воспроизведение» проходит 5 прогонов подряд без падений.
- `tests/test_transport` проходит на обычной сборке.
- Добавить в `tests/test_transport` (см. B6) проверку, что после всех
  вызовов `sigaction(SIGRTMAX)` указывает на `on_timeout`, а не `SIG_DFL`.

### A2. CLI `keyboard light on|off` инвертирован относительно железа

**Файлы:** `src/keyboard.c` — `as_keyboard_set_light_power_zones()`,
`as_keyboard_get_light_power_zones()`; `src/main.c` — `kb_set_main_power()`,
`print_kb_light()`, `print_kb_light_json()`, `kb_info_text()`, `kb_info_json()`;
`tests/test_cli.c:478`.

**Факт о железе.** Байт 0 команды `AS_K_SET_LED_POWER` — это флаг low power:
`1` = подсветка **выключена**, `0` = включена. Это подтверждено проверкой на
устройстве (коммит `4b194b9` «align keyboard light switch state» вводил именно
эту инверсию в GUI) и текстом README («low power mode»).

**Симптом.** `attackshark keyboard light on` **гасит** подсветку, а
`attackshark keyboard light off` **включает**. Чтение врёт так же:
`attackshark keyboard light` печатает `state off`, когда свет горит, и
`"on": 1` в JSON — наоборот.

**Причина.** API разговаривает в терминах «включено», а на провод кладёт байт
low-power без инверсии:
```c
uint8_t args[3] = { main_on ? 1 : 0, side_on ? 1 : 0, 0 };   /* 1 = выключить! */
```
CLI передаёт `light on` → `on = 1` → на устройство уходит `1` → свет гаснет.
GUI не пострадал только потому, что инвертирует **дважды**:
`req.light_on = !active` при записи (`as-keyboard-page.c:229`) и
`light_on = dev->light_on <= 0` при чтении (`:323`). Две ошибки взаимно
сократились. Тест `tests/test_cli.c:478` закрепляет инверсию
(`main_power == 1` после `light on`), поэтому правится вместе с кодом.

**Правка (одно место, чтобы ловушка не вернулась).** Инвертировать на границе
протокола, в `src/keyboard.c`:
- `as_keyboard_set_light_power_zones()`: `args[0] = main_on ? 0 : 1;`
  `args[1] = side_on ? 0 : 1;`
- `as_keyboard_get_light_power_zones()`: `*main_on = out[1] == 0;`,
  `*side_on = out[2] == 0;` (сохранив текущую обработку «не 0 и не 1» → -1)
- Убрать обе инверсии в GUI: `req.light_on = active`
  (`as-keyboard-page.c:229`) и `light_on = dev->light_on > 0` (`:323`).
- Удалить `as_keyboard_set_light_power()` из `src/keyboard.c` и
  `include/attackshark.h` — она нигде не вызывается (`grep` подтверждает) и
  содержит тот же зашитый `1`.

После этого имена (`main_on`, `side_on`, `light_on`) начинают соответствовать
смыслу, а CLI, его вывод и GUI согласованы без «двойных отрицаний».

**Проверка.**
- `tests/test_cli.c:478`: поменять ожидание на `main_power == 0` для
  `keyboard light on`; добавить кейс `keyboard light off` → `main_power == 1`.
- На железе: `attackshark keyboard light off` гасит, `light on` зажигает,
  `attackshark keyboard light` показывает `state on` при горящем свете.
- В GUI переключатель не должен изменить поведение (он был верным).

**Остаток, который нельзя закрыть без железа.** GUI при переключении
основной подсветки пишет второй байт константой `1`, не читая его
(`src/gui/as-store.c:1007`, `AS_OP_KB_LIGHT_POWER`), тогда как CLI делает
read-modify-write (`kb_set_main_power()`, `src/main.c:1340`). Заменить на
чтение (как в CLI) — 3 строки; что именно означает `1` для боковой зоны,
проверяется тем же приёмом на устройстве.

## B. Should fix

### B3. Зависший `.tmp` навсегда блокирует установку правил udev

**Файлы:** `src/udev.c` — `write_rules()`.

**Симптом.** После одной прерванной установки (отменённый пароль `pkexec`,
kill, потеря питания) кнопка «Исправить» и
`sudo attackshark permissions install` падают навсегда с
`cannot write /etc/udev/rules.d/70-attackshark.rules.tmp: File exists`.

**Причина.** `open(tmp, O_CREAT | O_EXCL)` без предварительной очистки.
`O_EXCL` здесь намеренный — он защищает от подмены через симлинк (есть тест
`test_udev_stale_symlink`), и эту защиту трогать нельзя.

**Правка.** Перед `open` убрать только *обычный* файл:
```c
struct stat st;
if (lstat(tmp, &st) == 0 && S_ISREG(st.st_mode)) unlink(tmp);
```
Симлинк по-прежнему отвергается через `O_EXCL`.

**Проверка.** `tests/test_detect` (тест на симлинк) остаётся зелёным;
добавить рядом тест: положить обычный файл `*.tmp` — установка должна
пройти и файл замениться.

### B4. `mouse info` может занять ~35 с и заблокировать очередь устройства

**Файлы:** `src/mouse.c` — `exchange()` (`RETRIES 5`, `REPLY_WINDOW_MS 250`),
`flash_io()`.

**Симптом.** Мышь ушла в сон посреди чтения — GUI «замирает» на полминуты,
запись настроек для этого устройства стоит в очереди, автообновление раз в
15 с упирается в тот же занятый поток.

**Цифры.** Блок настроек = 256 байт / 10 байт на пакет = 26 пакетов; худший
случай 26 × 5 × 250 мс ≈ 33 с, плюс четыре одиночные команды перед этим.

**Правка.** Один дедлайн на весь `flash_io`, а не попытки на каждый пакет:
`long deadline = now_ms() + 3000;` и в начале цикла
`if (now_ms() > deadline) return -ETIMEDOUT;`.

**Проверка.** `tests/test_mouse` (мок транспорта) — добавить кейс «устройство
перестало отвечать на середине блока»: вызов обязан вернуть `-ETIMEDOUT`
и уложиться в ~3 с.

### B5. Ползунки раскладки разрешают 0.00 мм, а записывают 0.1 мм

**Файлы:** `src/gui/as-key-dialog.c` — `make_slider()`, вызовы для
`Точка срабатывания` / `Точка отпускания` / `Rapid Trigger` / `Мёртвая зона`.

**Симптом.** Пользователь ставит «0.00 мм», а на устройстве оказывается
0.1 мм (или другое значение — зависит от шага прошивки). Следующее
обновление показывает не то, что было выставлено.

**Причина.** Минимум ползунков `0.0`; `as_kb_mm_to_raw(0.0)` возвращает `0`,
обратно `as_kb_raw_to_mm(0)` = `0.1`. CLI такое значение отвергает
(`parse_mm(act, 0.1, 4.0)`).

**Правка.** Минимум ползунков = один шаг, уже вычисляемый в `make_slider()`
(`0.005` / `0.01` / `0.1` по `dev->usb_version`). Для `deadzone` минимум
остаётся `0.0` — там ноль допустим протоколом.

**Проверка.** Выставить ползунок в минимум и убедиться, что показанное
значение равно записанному (`keyboard key N` в CLI после записи).

### B8. Разбор аргументов написан дважды

**Файл:** `src/main.c` — `validate_device_args()` (~120 строк) против
`cmd_mouse()` / `cmd_keyboard()`.

уже печатают usage и возвращают код 2.

**Проверка.** `tests/test_cli` — поведение CLI на мусорных аргументах не
должно измениться (тот же ненулевой код и сообщение).

## C. Nice to have

### C10. Вендорская коллекция ищется только в первых 512 байтах дескриптора

`include/attackshark.h` (`descriptor[512]`) + `read_file()` в `src/hidraw.c`.
У составных устройств дескриптор бывает длиннее — тогда `as_hid_has_vendor()`
вернёт 0 и устройство покажется «без настроек», молча. Либо увеличить буфер,
либо сравнивать `descriptor_len` с реальной длиной и явно сообщать об
усечении. На целевых моделях сейчас хватает.

### C11. `/usr/bin/udevadm` захардкожен

`src/udev.c` — `run_tool()`. На другой раскладке путей `posix_spawn` вернёт
`-ENOENT`, а код трактует это как «udevadm нет» и возвращает успех: правила
записаны, но не применены, пользователь об этом не узнает. Искать в `PATH`
или проверить `/bin/udevadm` и `/sbin/udevadm`.

### C12. Слияние узлов возможно при усечённом `uevent`

`src/hidraw.c` — `device_key()`: узел без `HID_PHYS` получает ключ по пути,
поэтому два интерфейса одной клавиатуры дадут две строки в списке. На
реальной машине не воспроизведено, отмечено как риск, а не как баг.

### D14. Демо-свич и его подписи невидимы на светлой теме

**Файлы:** `src/gui/as-key-dialog.c` — `demo_draw()`.

**Проблема.** Цвета захардкожены под тёмную тему: текст `0.95,0.95,0.95` на
светлом фоне даёт **1.07:1**, подпись «Срабатывание» — 1.83:1, «Отпускание» —
1.44:1. На светлой теме (libadwaita по умолчанию следует системе) блок
«Проверка нажатия» выглядит пустым прямоугольником. На тёмной — 13.87:1.

**Правка.** Не хардкодить: брать цвета через
`gtk_style_context_lookup_color(gtk_widget_get_style_context(d->demo_area),
"window_fg_color"/"accent_bg_color"/"warning_color")` и перерисовывать по
сигналу `notify::dark` от `adw_style_manager_get_default()`.

**Проверка.** Отрисовать `ATTACKSHARK_GUI_KEYDIALOG=1 ATTACKSHARK_GUI_SHOT=…`
на светлой и тёмной теме; на обеих текст читается.

### D15. Легенда раскладки и индикация ниже нормы контраста

**Файл:** `src/gui/as-key-dialog.c` — `make_legend()`, `load_css()`.

**Проблема.** Markup с зашитыми `#2ec27e` (2.20:1), `#e66100` (3.31:1),
`#3584e4` (3.61:1) при шрифте 11 px; белый текст на заливке «нажата» — 2.65:1.
Все три ниже 4.5:1, а зелёный и оранжевый — даже ниже 3:1 для нетекстовой
графики. На светлой теме индикаторы почти неразличимы.

**Правка.** Использовать именованные цвета темы (`@success_color`,

индикатора (точка/квадрат/обводка) уже разная — её и достаточно как
нецветовой признак.

**Проверка.** Те же скриншоты, что в D14; визуально индикаторы читаются.

### D16. Раскладку нельзя использовать с клавиатуры

**Файл:** `src/gui/as-key-dialog.c` — создание кейкапов:
`gtk_widget_set_focusable(button, FALSE)`.

**Проблема.** Все 68 клавиш исключены из обхода фокуса, поэтому выбрать
клавиши можно только мышью. Это сделано, чтобы нажатая на клавиатуре
клавиша дошла до `on_test_pressed`, но цена — недоступный интерфейс для
тех, кто работает без мыши.

**Правка.** Оставить кейкапы фокусируемыми и переключать их пробелом
(`togglebutton` это уже умеет), а «проверку нажатия» включать
переключателем (демо-свич уже есть) — тогда обработчик клавиш ставится
только когда демо активно.

**Проверка.** Пройти весь диалог Tab'ом и выбрать пару клавиш без мыши.

### D17. «Проверка нажатия» активирует виджеты: Space/Enter могут применить запись

**Файл:** `src/gui/as-key-dialog.c` — `on_test_pressed()` возвращает `FALSE`.

**Проблема.** Событие не поглощается, поэтому, пока фокус на кнопке
«Применить к выбранным», нажатие Space (HID 44) идёт и в обработчик проверки,
и в GTK — кнопка активируется и **пишет настройки на клавиатуру**. То же с
Enter при фокусе на любой активируемой строке.

**Правка.** Возвращать `TRUE` для клавиш, которые есть в раскладке (то есть
поглощать событие), и в любом случае не активировать запись, пока активен
демо-свич.

**Проверка.** Открыть раскладку, сфокусировать «Применить», нажать пробел —
записи нет, кейкап Space подсвечен.

### D18. В демо печатается обрывок предыдущей строки

**Файл:** `src/gui/as-key-dialog.c` — конец `demo_draw()`.

**Проблема.** `buf` заполняется подписью «состояние: …», а затем
переиспользуется под имя клавиши только внутри цикла поиска `demo_key`.
Если `demo_key` не совпал ни с одним кейкапом (аналоговый поток отдаёт
позиции, которых на 68-клавишной раскладке нет), печатается старый текст:
«Клавиша: состояние: отпущена».

**Правка.** Заполнять `buf` значением по умолчанию (`"—"`) перед циклом.

**Проверка.** Включить демо и нажать клавишу вне раскладки — подпись не
склеивается.

### D19. GUI молча зажимает значения устройства в диапазон контрола

**Файлы:** `src/gui/as-key-dialog.c` (`KEY_MAX_TRIGGER 2.0`,
`make_slider`), `src/gui/as-ui.c` (`as_ui_slider_set`), `src/gui/as-mouse-page.c`
(LOD 1..4), `src/gui/as-keyboard-page.c` (debounce 0..20).

**Проблема.** `as_ui_slider_set` не только показывает, но и **записывает
прижатое значение** в переменную, которую потом отправляет `on_apply`.
Документированный и измеренный на железе `release = 2.50 мм`
(`docs/GUI.md`) при открытии раскладки превращается в `2.00`, и достаточно
нажать «Применить», чтобы записать это на клавиатуру. То же для
`rt_press`/`rt_release` (потолок 2.0 против 4.0 в CLI) и для debounce/LOD
(20 мс и 1..4 против 0..255 в CLI).

**Правка.** Не расширять молча: если значение вне диапазона, показать его в
подписи как есть (значение + пометка «за пределами ползунка») и не менять
`*out`, либо поднять границы ползунков до пределов протокола (4.0 мм,
debounce 255).

**Проверка.** Записать `keyboard key 9 --release 2.5`, открыть раскладку,
нажать «Применить» без правок — значение на клавиатуре остаётся 2.50.

### D20. Значения не сбрасываются, когда устройство уходит в offline

**Файлы:** `src/gui/as-keyboard-page.c` — `update_page()` (`row_profile`);
`src/gui/as-mouse-page.c` — `update_page()` (`row_profile`, `row_dpi_now`).

**Проблема.** `if (dev->profile >= 0) …` без `else`: когда мышь спит и
состояние не прочитано (`profile = -1`), в строках остаётся последний
профиль предыдущего опроса, хотя остальные поля уже показывают «—».
Пользователь видит смесь свежих и устаревших данных.

**Правка.** Добавить `else as_ui_row_set_value(row, "—")`, как уже сделано
для `row_firmware` и `row_revision`.

**Проверка.** Отключить мышь при открытой странице: все строки состояния
показывают «—».

### D21. Snap Tap остаётся активным при выключенном переключателе

**Файл:** `src/gui/as-keyboard-page.c` — `update_page()` (блок `snap_group`).

**Проблема.** Чувствительность `row_snap_mode`, `sw_snap_full` и кнопок
выбора клавиш не зависит от `sw_snap`. Пользователь выбирает пару и режим
при снятой галочке — ничего не происходит, а при её включении применяется
то, что было выставлено молча. Если ключи не выбраны, `apply_snap` молча
выходит, и галочка отскакивает обратно на следующем обновлении.

**Правка.** `gtk_widget_set_sensitive(…, mode >= 0 || snap_picked)` для
контролов пары и подсказка под галочкой, если пара не выбрана.

**Проверка.** Снять галочку Snap Tap — выбор клавиш и режима недоступен.

### D22. Тост на каждую ошибку автообновления

**Файл:** `src/gui/as-window.c` — `on_store_error()`.

**Проблема.** Автообновление раз в 15 с; если клавиатура перестала отвечать
(типичный случай из README — занятый эндпоинт), тост с одной и той же
ошибкой всплывает каждые 15 с и перекрывает интерфейс.

**Правка.** Помнить последнюю пару (path, message) и не повторять тост,
пока сообщение не сменилось.

**Проверка.** Оставить клавиатуру занятой OpenRGB на минуту — тост один.

### D23. Демо-поток замирает на каждом автоопросе

**Файл:** `src/gui/as-store.c` — `config_begin()` / `store_request()`.

**Проблема.** Любой опрос устройства (в том числе плановый, раз в 15 с)
поднимает `config_pending`, что закрывает `analog_fd` и останавливает
ленту; после опроса `config_end()` поднимает её заново. На клавиатуре опрос
включает чтение семи таблиц хода, то есть заметно дольше заявленных в
`docs/GUI.md` «~0.2 с»; демо-свич в это время замирает.

**Правка.** Либо не останавливать поток на плановый опрос (читать состояние
при работающем демо), либо в демо показывать «обновление…» вместо замершей
картинки.

**Проверка.** Включить демо и подождать два цикла автообновления — движение
не прерывается.

### D24. Утечки `GtkStringList` (5 на страницу и диалог)

**Файлы:** `src/gui/as-keyboard-page.c` (`mag`, `modes`, два списка подсветки),
`src/gui/as-key-dialog.c` (`types`), `src/gui/as-ui.c`
(`as_ui_light_list_for`).

**Проблема.** `adw_combo_row_set_model()` берёт свою ссылку, а созданная в
вызывающем коде — никогда не освобождается.

**Правка.** Обернуть: `adw_combo_row_set_model(row, model); g_object_unref(model);`
либо отдавать владение в `as_ui_combo()`.

**Проверка.** Открыть/закрыть страницу клавиатуры 50 раз — RSS не растёт.

### D25. Диапазоны GUI и CLI расходятся

**Файлы:** `src/gui/as-keyboard-page.c` (debounce 0..20),
`src/gui/as-mouse-page.c` (debounce 0..20, LOD 1..4),

**Правка.** Решить один раз (по фактическому поведению прошивки), описать в

**Проверка.** Значения из GUI не отвергаются устройством, а CLI не
принимает того, что устройство молча игнорирует.

## E. Прочее (найдено во втором проходе)

### E26. `#` в `/etc/attackshark.conf` съедает значение

**Файл:** `src/main.c` — `cmd_apply()`: `line[strcspn(line, "#\n")] = 0;`

**Проблема.** Символ `#` считается началом комментария в любом месте строки,
хотя `parse_color()` его принимает. Проверено: строка
`keyboard light --color #00a0ff` превращается в `keyboard light --color `,
и строка профиля падает с «color must be RRGGBB».

**Правка.** Обрезать комментарий только если `#` стоит в начале строки или
после пробела перед первым аргументом, либо убрать `#` из `parse_color()`.

**Проверка.** `apply` с `--color #00a0ff` применяет синий цвет.

### E27. Документация и код расходятся в том, отдаёт ли прошивка состояние выключателя

**Файлы:** `docs/GUI.md` («Сама прошивка состояние выключателя не отдаёт
(возвращает эхо), поэтому галочка помнит последнее значение локально»)
против `src/gui/as-keyboard-page.c:update_page()` + `fill_keyboard()` — код
читает `get_light_power_zones()` при каждом опросе и **перезаписывает**
галочку из устройства.

**Проблема.** Если документация верна, то через 15 с галочка сама
переключится на значение из эха запроса. Если верен код, то неверна
документация. Обе стороны описаны как проверенные на железе.

**Правка.** Проверить на устройстве: `attackshark keyboard light` при
заведомо выключенной подсветке. Затем либо убрать чтение из `update_page`
(и хранить состояние локально, как описано), либо поправить документацию.

**Проверка.** Выключить подсветку, подождать два автообновления — галочка не
меняется.

### E28. `-EBUSY` показывается как «Device or resource busy»

**Файл:** `src/util.c` — `as_strerror()`.

**Проблема.** Отдельного текста для `EBUSY` нет, поэтому редкая, но важная
для диагностики ситуация «не нашлось свободного RT-сигнала для таймаута»
(`hidraw.c`, все RT-сигналы заняты) превращается в невнятное
«Device or resource busy».

**Правка.** Добавить `case EBUSY: return "no free real-time signal for the I/O timeout";`.

**Проверка.** `grep` по тестам про `-EBUSY`; в `test_transport` ожидаемый код
уже есть — проверить текст.

### E29. `write_all` может крутиться вечно

**Файл:** `src/udev.c` — `write_all()`.

**Проблема.** Если `write()` вернёт 0 при `len > 0`, цикл не завершится.
Для обычного файла это почти невозможно, но установка правил идёт под root
и зависание там недопустимо.

**Правка.** `if (n == 0) return -EIO;`.

**Проверка.** Тест в `tests/test_detect` с мок-`write`, возвращающим 0.

### E30. `--json` и текст дают разные коды возврата при отсутствии устройств

**Файл:** `src/main.c` — `cmd_list()`.

**Проблема.** Текстовый режим возвращает 1, `--json` печатает `[]` и
возвращает 0. Скрипт, переключившийся на JSON, перестаёт замечать
«устройств нет».

**Правка.** Выбрать одно поведение (разумно 0 для обоих, но одинаково) и
описать в README.

### E31. `as_keyboard_get_keymatrix()` никогда не возвращает ошибку

**Файл:** `src/keyboard.c`; потребители — `src/main.c` (`have_matrix`,
ветка `поз.%d`), `src/gui/as-store.c` (`matrix_valid`).

**Проблема.** Функция всегда возвращает 0 (при неудаче подставляет
`default_matrix`), поэтому у вызывающих мёртвые ветки: `have_matrix` всегда 1,
`h->matrix_valid` всегда 1, `поз.%d` не печатается никогда.

**Правка.** Либо возвращать признак «взято с устройства / подставлено», либо
убрать обработку ошибок у вызывающих.

### E32. Диалог раскладки открывается много раз

**Файл:** `src/gui/as-keyboard-page.c` — `on_layout()`.

**Проблема.** Каждый клик по «Открыть…» создаёт новое модальное окно; они
складываются друг на друга, каждое держит обработчики `store` (и своё
демо-потоковое состояние).

**Правка.** Хранить слабую ссылку на диалог и `gtk_window_present()` вместо
создания нового.
